# S4 · 数据 + 实验

> 纪律声明：现在是 2017 年夏，方法骨架在 S3 定型，我开始准备数据与跑实验。我不知道 BLEU 会到多少；我只知道 Table 2 现在的样子还什么都没写。

## 【数据轨】

**1. 数据从哪来：全部公开，自建零成本**

两条赛道都用 WMT 2014 官方数据：
- EN-DE：4.5M 句对，用 byte-pair encoding (BPE) 切成约 37,000 个共享 subword token（【可查证】§5.1）。共享词表的意思是源端与目标端用同一份 token 列表——这减少了目标端 OOV 的麻烦，也让 embedding 共享（S3 四象限表里的那一项）变得自然。
- EN-FR：36M 句对（比 EN-DE 大八倍），用 word-piece 切成 32,000 词表（【可查证】§5.1）。

当时没有任何"自建 vs 公开"的纠结：WMT 是这条赛道的唯一公认考场，自建数据等于自己出题。EN-DE 选 BPE、EN-FR 选 word-piece 这两件事**不是我们做的研究决策，是当时社区里各自阵营的默认配置**（【合理重构】依据：BPE 引 [31] Sennrich 2015，word-piece 引 [38] GNMT，两篇都是各自赛道的前作默认）。S8 复核口径：论文没有把"为什么 EN-DE 用 BPE、EN-FR 用 word-piece"写成动机句。

**2. 清洗与筛选：按近似句长分桶**

没有花式的数据清洗叙事。唯一的"规则"是 batch 的构造方式：把句对按**近似序列长度**分桶，每个 batch 装约 25,000 源 token + 25,000 目标 token（【可查证】§5.1）。这条规则的动机是显存效率——句长差太大的 batch 要么短句被 pad 浪费、要么长句放不下。这条规则有没有把好东西滤掉？【合理重构】我当时的担心是：分桶会让同一 batch 内的句长过于一致，可能减少梯度多样性。实际跑下来没出可观测的问题，就没改。这是**一次未爆的雷**，记入 S5。

**3. 数据规模：不是算出来的，是"只有这么多"**

4.5M 句对就是 WMT14 EN-DE 的全部；36M 就是 EN-FR 的全部。我们没有做"要不要砍数据"的决定——用全量是默认且唯一严肃的选项（【合理重构】）。

## 【实验轨】

**4. 核心问题与实验倒推**

核心问题一句话：**没有循环没有卷积的架构，能不能在翻译质量上打赢有循环有卷积的 SOTA？** 倒推需要的实验：
- 一个 big 配置冲 BLEU（对比所有已发表系统，含 ensemble）；
- 一个 base 配置证明"小模型也有竞争力"（且训练成本只有 10^18–10^19 FLOPs，比 GNMT 低一到两个数量级）；
- 一组消融（Table 3）回答"每个组件是不是 necessary"——这是投 NIPS 的门票。

**5. Baseline 选谁**：GNMT + RL、ConvS2S、ByteNet、MoE、Deep-Att + PosUnk（【可查证】Table 2 全部列出）。最怕被谁比下去：ConvS2S——它与我们同属"去循环"阵营，输了它就等于"卷积才是去循环的正确姿势"（【合理重构】，依据：S2 惊魂时刻）。

**6. 超参数怎么定的**

**7. 消融：每个被拆的组件在回应哪个质疑**

Table 3（newstest2013 dev，EN-DE）：
- **行 (A)** 变头数（1/4/16/32）与 d_k（512/128/32/16/...）：回应"多头是不是花架子"。单头比最佳差 0.9 BLEU；32 头也降——头太多质量也掉（【可查证】§6.2 原句）。
- **行 (B)** 变 d_model（16/32/256/1024）：回应"模型大了是不是更好"。256 宽 26.0 BLEU 比 base 25.8 高，1024 宽 26.0 也高——"big is better"大致单调。
- **行 (C)** 层数 2 vs 6 vs ？：回应"深度"。2 层 23.7，显著差。
- **行 (D)** dropout 0.0 vs 0.2 vs 0.1：回应"dropout 是否 necessary"。0.0 时差 1.2 BLEU（24.6 vs 25.8）。
- **行 (E)** 学习式位置编码 vs 正弦：回应"正弦是不是必要的"。25.7 vs 25.8——几乎一样。

每条消融对应一个 S3/S4 的真实质疑，没有一个是为了填表而填（【合理重构】）。

**8. 实验崩了的那一次**

【合理重构】大 d_model 试跑（Table 3 行 B 的 1024 宽配置）在训练约 20K 步时 loss 突跳到 NaN。排查路径：先查学习率（从 1e-3 降到 5e-4，又 NaN）→ 再查梯度范数（发现某几步的梯度范数从个位数跳到 10^3 量级，然后 NaN）→ 定位到 multi-head 里某个头的 softmax 输出在个别 batch 上几乎 one-hot，反向时 0 的对数炸了 → 临时修复：warmup 从 1K 提到 4K，让前期步数小一点；并把 Adam 的 β2 从 0.999 调到 0.98，让二阶矩估计对新梯度更敏感、异常步更快被平均掉。

这条修复链的最后一步——warmup=4000 与 β2=0.98——就是 §5.3 和 §5.4 现在写着的值（【可查证】）。**我们当时不知道这个组合是不是唯一解，只知道它能训**。这个"不知道"在 S8 会成为一个核查点：warmup=4000 的选择有没有在任何地方被写成"试过 1K/2K/8K 后的最优"？没有（【可查证】§5.3 只有最终值）。
